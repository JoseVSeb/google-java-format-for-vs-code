# google-java-format on CheerpJ (experiment)

Runs the **official latest google-java-format release** on a browser JVM, with no server and no
local Java. Groundwork for supporting this extension on VS Code for the Web, where spawning a
native binary or a local JVM is impossible.

Nothing here touches the shipped extension. The directory is self-contained: `./build.sh`
produces one jar, `./verify.sh` checks it, `./serve.sh` opens the demo page.

## The problem

Two hard constraints do not meet:

| | Requires | Provides |
|---|---|---|
| google-java-format 1.36.1 | Java 21 bytecode, plus JDK 21 `jdk.compiler` internals (`com.sun.tools.javac.*`) reached through `--add-exports` | |
| CheerpJ 4.3 | | Java 8, 11 and 17 runtimes; Java 21 is on their roadmap, not shipped |

Loading the release jar as-is fails three ways: its own classes are class file version 65 and a
Java 17 JVM rejects them; the formatter binds to javac internals that only exist in JDK 21 (its
tree visitor references `JCAnyPattern`, added after 17); and CheerpJ's launcher has nowhere to
put `--add-exports`, so even a matching `jdk.compiler` would stay encapsulated.

## The approach

`build.sh` takes the untouched `-all-deps` jar from Maven Central and JDK 21's compiler modules
from a local JDK image, and writes a single bundle:

1. **Relocation.** `com.sun.tools.javac`, `com.sun.source`, `javax.lang.model`, `javax.tools`,
   `javax.annotation.processing` and `jdk.internal.opt` move under `gjfweb.shaded.`, and
   google-java-format's references follow them. The formatter now carries its own JDK 21 parser
   instead of borrowing the host's, so the host's Java version stops mattering, nothing can be
   shadowed by a platform module, and `--add-exports` is unnecessary because nothing lives in a
   named module any more.
2. **Retargeting.** Class files above the target version are rewritten to class file 61 (Java 17).
3. **Bootstrap rewriting.** Pattern-matching switch (`java.lang.runtime.SwitchBootstraps`, final
   in Java 21) is redirected to `gjfweb.runtime.SwitchShim`, which reimplements the documented
   `typeSwitch` / `enumSwitch` semantics on Java 17 APIs. `java.lang.MatchException` becomes
   `gjfweb.runtime.MatchException`, since `java.lang` cannot be extended from a jar.
4. **API shims.** The five Java 21 library calls in the bundled code (`StringBuilder.repeat` and
   four `SequencedCollection` methods on `List`) become static calls into `gjfweb.runtime.ApiShims`.

The result is `dist/gjf-cheerpj.jar`, 7.6 MB, class file 61 throughout, with `gjfweb.api.BrowserFormatter`
as its JavaScript-facing entry point.

## Results

Measured in this repository on OpenJDK 17.0.20, against the official jar on OpenJDK 21.0.10:

| Check | Result |
|---|---|
| Classes at class file 61 or below | 4600 of 4600 |
| References to the JDK compiler outside the relocated prefix | 0 |
| Platform references resolvable on Java 17 | 35010 checked, 0 unexpected gaps |
| Corpus formatted identically by bundle-on-17 and official-on-21 | 667 of 667 files, byte for byte |
| Browser entry point vs the official CLI (`--aosp`, `--lines`, defaults) | 45 of 45 invocations identical |
| Worker protocol checks in Chromium | 10 of 10 |
| Wall clock over the corpus | 12.8 s bundled on Java 17, 10.9 s official on Java 21 |

The corpus is google-java-format's own sources plus Guava's, the extension's fixtures, and
`testdata/ModernSyntax.java`. That last file uses record patterns, guarded `case` labels, `case null`
and sealed interfaces: Java 21 syntax a Java 17 compiler cannot parse. It formats correctly on the
Java 17 JVM, which is the direct evidence that the bundled JDK 21 parser is the one doing the work.

**The browser leg is still unverified here.** This container's egress policy blocks `cjrtnc.leaningtech.com`,
so CheerpJ's runtime cannot be fetched here and the demo page reports exactly that. Everything up
to the JVM boundary is verified on a stock Java 17 JVM, which is the runtime CheerpJ implements.
Run `./serve.sh` on a machine with network access to finish the check; the page's **Run self-test**
button formats the fixtures in the browser and compares against output generated by a desktop JVM
from the same jar, so a green self-test means the two JVMs agree byte for byte.

## Running in a Web Worker

VS Code for the Web runs extensions inside a Web Worker, so that is the shape this targets.
CheerpJ has supported workers since 3.0rc2: `importScripts` the loader and use the API as
usual, with the one restriction that nothing DOM-dependent works. Headless library mode, which
is all the formatter needs, is explicitly among the supported uses.

- `web/gjf-worker.js` boots CheerpJ inside a dedicated worker and serves a request/response
  protocol over `postMessage`. Requests are queued, because the JVM call is synchronous inside
  CheerpJ and pretending otherwise would only hide it.
- `web/gjf-client.js` is the page-side wrapper. Its shape is the extension's own interface,
  `format(text, range?, signal?)`, with the range being VS Code's 1-based inclusive lines, so
  the browser backend can sit behind the same interface as the native binary.
- `web/gjf-main-thread.js` is the same interface without the worker, for a host that forbids
  workers or forbids a worker fetching a remote script. It blocks whatever thread it runs on,
  so prefer the worker.

`cheerpjInit` must be called with `status: "none"` off the main thread: the default loading
indicator draws into a document the worker does not have.

Abort deserves a note. A CheerpJ call cannot be interrupted, so aborting rejects the caller's
promise and drops the reply; the JVM finishes the work regardless. Cancellation is about the
caller, not about reclaiming the time.

## Tests

```sh
./test.sh           # worker protocol, in a browser, no network needed
./test-cheerpj.sh   # the same bundle under the real CheerpJ runtime
```

`test.sh` runs ten checks in Chromium against `web/test/mock-cheerpj.js`, a stand-in that
defines the same globals with the same async shapes as CheerpJ's loader. It covers the parts
that are easy to get wrong and invisible until they bite: option and line-range positions
reaching the Java call, replies correlating by id under concurrency, a parse error rejecting
only its own call, abort not poisoning the worker, and an unreachable runtime producing a
message that names the cause. It does not run Java, and does not pretend to.

`test-cheerpj.sh` is the release gate: it boots the real runtime, formats the fixtures in the
browser and compares against output a desktop JVM produced from the same jar, so a mismatch
means the two JVMs disagree. It needs the CDN, and fails with that reason when the CDN is
unreachable, which is what happens in this container.

## Running it as a pipeline

The build takes two inputs and produces one file, with no coupling to this repository:
a google-java-format release fetched from Maven Central at build time, and a JDK 21 image
for the compiler modules. Point `GJF_VERSION` at a release and you get the matching bundle.
`ci/release-bundle.yaml` is a template workflow that polls Maven Central, builds, verifies
and publishes the jar as a release asset; it is inert where it sits and only runs once moved
into `.github/workflows/`.

Two properties make that safe to run unattended:

- **The build is byte-reproducible.** Entries are sorted, timestamps are zeroed, and the
  manifest is written as an ordinary entry, so two builds from the same inputs hash the same.
  Nothing is appended after assembly: the JavaScript-facing API is compiled against a staged
  bundle and folded in by a second pass, which the transformations tolerate because they are
  idempotent. A pipeline can therefore compare a rebuild to a published asset by hash.
- **`verify.sh` is a real gate.** The API scan fails the build when a new release calls a Java
  API the target runtime lacks, which is the likely way a future release breaks this, and the
  corpus comparison fails it if any transformation changed a formatting decision.

The bundle records what it was made from, so a consumer can check provenance without unzipping
class files:

```
Bundle-Gjf-Version: 1.36.1
Bundle-Compiler-Jdk: 21.0.10+7-Ubuntu-124.04
Bundle-Target-Class-Version: 61
Bundle-Relocation-Prefix: gjfweb.shaded.
```

The JDK line matters. The bundled parser is whatever javac the build machine's Java 21 image
carried, so pin the distribution and version in CI rather than taking the runner's default.

## Usage

```sh
./build.sh     # download the official release, build dist/gjf-cheerpj.jar
./verify.sh    # class versions, relocation, API scan, 667-file output equivalence
./serve.sh     # http://localhost:8000/web/
```

`build.sh` reads `GJF_VERSION` (default: latest on Maven Central), `JDK21_HOME` and `JDK17_HOME`.
Building needs a JDK 21+ image for the compiler modules and a JDK 17 for the shims and checks.

From JavaScript, the worker client is the whole surface:

```js
import { createFormatter } from "./gjf-client.js";

const formatter = createFormatter({ jarUrl: "../dist/gjf-cheerpj.jar", javaVersion: "17" });
await formatter.version();                    // "1.36.1"
await formatter.format(source);               // whole file, the CLI's defaults
await formatter.format(source, [3, 9]);       // lines 3 to 9, as VS Code passes them
await formatter.format(source, undefined, signal, { style: "AOSP" });
formatter.dispose();
```

Underneath, the Java entry point is four static methods, reachable directly if you would rather
not use the client:

```js
await cheerpjInit({ javaVersion: "17", status: "none" });
const lib = await cheerpjRunLibrary("/app/dist/gjf-cheerpj.jar");
const api = await lib.gjfweb.api.BrowserFormatter;

await api.version();
await api.formatDefault(source);
await api.format(source, "GOOGLE", true, true, true, true, 0, 0); // {"ok":true,"output":"…"}
await api.formatOrThrow(source, "AOSP", true, true, true, true, 3, 9);
```

`format` answers with JSON rather than throwing because a rejected CheerpJ promise carries a Java
exception that is awkward to read from JavaScript. The pipeline behind it is the driver's own:
format the selected ranges, fix imports, reflow long strings, with the driver's defaults.

## Layout

```
build.sh            builds the bundle
verify.sh           checks it against the official release
serve.sh            serves the demo
tools/src           BundleBuilder (the relocate/retarget/rewrite pass, ASM based)
                    CorpusRunner and ApiScanner (verification)
runtime/src         SwitchShim, MatchException, ApiShims — the Java 17 stand-ins
api/src             BrowserFormatter — what JavaScript calls
web/                gjf-worker.js and gjf-client.js (the worker backend),
                    gjf-main-thread.js (fallback), demo page, mock loader for tests
test/               browser tests: worker protocol, demo page, CheerpJ release gate
testdata/           Java 21 syntax fixture
ci/                 template release workflow, inert until moved into .github/workflows/
```

## Known limitations

- **CheerpJ has no Java 21 runtime yet.** Every transformation above exists only to bridge that
  gap. When CheerpJ ships Java 21, drop the retargeting and the shims and keep the relocation,
  which is still worth having: it is what removes the `--add-exports` requirement.
- **Three javac classes cannot link on any classpath.** `AnnotationProxyMaker`'s exception proxies
  extend `sun.reflect.annotation.ExceptionProxy`, which java.base exports to nobody. Only
  annotation processing reaches them; parsing and formatting never do. They are listed in
  `verify-allowlist.txt`, and the API scanner fails the build on anything else.
- **Bundle size is 7.6 MB.** Most of it is javac. The formatter needs the parser, the lexer and
  the diagnostic machinery, so trimming is possible but not trivial. CheerpJ fetches and JIT
  compiles it on first use.
- **Licensing needs a decision before this ships.** The bundle mixes google-java-format
  (Apache 2.0) with OpenJDK compiler classes (GPL v2 with Classpath Exception), and CheerpJ itself
  is proprietary — free for personal use and evaluation, licensed for commercial distribution.
- **The worker path is written and tested, but not yet against real CheerpJ.** The protocol is
  covered in a browser with a stand-in loader; `./test-cheerpj.sh` closes the remaining gap on a
  networked machine. Two things after that are still unknown: whether VS Code's extension host
  permits a nested worker fetching a remote script under its content security policy, and whether
  a self-hosted copy of the runtime is needed to satisfy it.
